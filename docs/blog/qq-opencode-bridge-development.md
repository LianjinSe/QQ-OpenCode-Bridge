QQ-OpenCode-Bridge 已经整理成了公开仓库。它通过 NapCat 接收 QQ 消息，把任务交给 OpenCode v2，再将文字和文件发回原来的聊天。围绕这条链路，后来陆续补上了群聊权限和任务恢复，也接入了长期记忆与文档知识库，还做了一个独立的管理台。

前面写过一篇偏聊天体验的记录。这篇换个角度，整理这个项目在工程上是怎样一步步改过来的。开发过程中由 Codex 协助实现和验证，我负责确定使用方式、检查结果，再根据实际使用继续提修改。

项目地址：[LianjinSe/QQ-OpenCode-Bridge](https://github.com/LianjinSe/QQ-OpenCode-Bridge)。

## 先把一条消息走通

项目的基本分工一直很明确。NapCat 负责 QQ 连接，Python 桥接负责消息路由和任务状态，OpenCode 负责会话与 Agent 执行。聊天模型通过远程 API 调用，桥接本身不加载模型权重。

```text
QQ 消息
  → NapCat / OneBot v11 正向 WebSocket
  → Python 桥接：准入、上下文、任务队列
  → OpenCode v2：模型与工具执行
  → 桥接发送队列
  → 原私聊或群聊
```

先接通文字之后，使用中的要求逐渐具体起来。私聊要能延续上下文，不同群不能串话，群里有人引用一张图片时，也得把那张图片交给模型。机器上还有其他 QQ 服务，桥接需要按前缀避开已经由其他服务处理的消息。

这些逻辑放在接收入口处理。消息先经过白名单和触发条件检查，再准备附件、创建任务。没有被准入的消息，不应该先下载一遍文件，再决定忽略。

OpenCode 也有自己的版本边界。项目使用 v2 的会话、权限、表单和指令接口，启动时检查实际 API。安装了一个名字叫 OpenCode 的程序，并不足以说明它能与这套桥接配合。

## 群里共享话题，权限跟着发起人走

私聊天然容易确定对象，群聊会复杂得多。同一个群里，前一条任务可能由管理员发起，下一条就来自普通成员。大家需要共享话题，但不能共享管理员身份。

我把群聊做成了同群共享上下文，任务始终绑定 NapCat 提供的真实发送者。群白名单控制哪些群可以使用，正常请求还需要真实 @ 机器人；没有 @ 的消息只在有限窗口内作为背景保存。

每一轮重新确定当前发起人和权限。管理员本人发起的任务可以按配置自动授权，普通成员需要修改文件或执行未确认只读的操作时，仍由同群管理员批准。历史里出现过一次批准，不会变成这个群以后永久拥有的权限。

这些是项目当前的默认规则。如果有自己的需求，建议按使用场景修改权限，不建议完全不设置权限。白名单和管理员可以先通过配置调整，需要改变审批或工具范围时，再修改对应的后端策略并验证；只改人格里的说明不会改变实际权限判断。

引用也遵守相同原则。聊天记录中的“我是管理员”，只是一段待处理的文字。昵称、附件和文档都不能替代服务端确认的身份。后面接入其他工具时，这条规则继续沿用。

## 开始处理文件，也开始区分“做完”和“发出”

文件能力让桥接多了不少状态。收到图片要保存，引用原消息要核对范围，合并转发还要处理嵌套记录。现在直接引用的媒体会作为实际附件提交给 OpenCode；纯文字或合并转发的记录则保存成聊天记录 JSON 附件，正文只保留本次要求和必要说明。

分享卡片另走一条简短的路径。直接引用网页分享时，只提取有效的 HTTP(S) 链接。桥接不会因为卡片上有标题和摘要，就宣称已经读过网页。

回传文件最初依赖回复中的交付标记，后来换成了原生 `qq_send_files` 工具。模型准备好文件后主动提交，桥接从当前活动任务确定收件聊天，模型不需要再填写 QQ 号或群号。

这次调整也把发送状态说清楚了。工具返回 `queued`，只表示文件快照已经保存并排队。文件生成完成与上传缓存成功要区分，实际发送确认还得单独判断。即时模式可以在任务结束前开始发附件，普通模式则等任务成功后再交付；最终正文仍受实际交付结果约束。

每次调用都有持久化回执，同一个调用重放会复用快照，多个调用累计计算数量和大小。超时之后如果无法确定 QQ 是否已经收到，就保留“不确定”状态，不换一个调用编号再发一次。图片和普通文件都沿用这套规则。

生图也放进了这条链路。脚本读取配置和供应商凭据，在本轮目录里生成文件，再交给附件工具发送。生图成功的结果不能直接代替交付确认。

## 服务重启以后，任务不能只剩一句“收到”

接通模型后，服务重启和网络中断就成了日常维护必须面对的问题。用户已经提交的任务，需要知道停在哪一步；正在发送的回复，也不能因为桥接重启就再发一遍。

桥接用 SQLite 保存任务状态和出站队列。提交给 OpenCode 的文本、提交 ID，以及附件快照都与原任务绑定。恢复时复用已经冻结的输入，不重新读取一遍 QQ 消息来拼出另一个请求。

任务完成和对应回复进入发送队列放在同一事务中。记忆归档位于另一套存储，跨库部分保留可重试的补偿标志。这样可以单独判断任务是否结束、回复是否待发送，以及归档是否还没完成。

恢复仍有边界。外部操作可能已经执行却没有返回确认，本地数据库无法替外部系统给出答案。遇到这种情况，先保留现场和回执，再核实状态，比自动重试更合适。

## 把长期记忆改成按需调用的工具

对话历史和长期记忆承担不同的用途。新开一个会话可以换话题，同时保留用户明确要求记住的信息。把全部档案每轮塞进消息里，会让普通聊天背上越来越长的背景。

后来记忆改成了模型可自主调用的工具。需要回忆时先搜索，要保存或纠正时再写入；查原话和查每日摘要也各有入口。普通轮次结束后保留原始文字归档，不再让另一个提取器每轮自动生成事实。

存储使用 Mem0 和 PostgreSQL / pgvector，写入保持 `infer=False`。桥接先核对所有者、来源和可见范围，再保存筛选后的内容。用户资料、助手资料和共同经历分别标记主体，避免同一个字段互相覆盖。

证据规则是在使用中逐渐收紧的。用户原话可以支持用户事实，助手说“已经完成”却不能单独证明外部操作成功。需要引用历史或工具结果时，先用 `memory_evidence` 取到对应证据，再提交写入；失败结果可以保存为失败经验，不能改写成已经学会的能力。

遗忘也需要管住来源。删掉一条记忆后，旧聊天不能在下一次整理时把同样的内容重新学回来。普通遗忘保留原始聊天，明确清除原文则使用另一条管理操作；这些操作都不承诺清掉备份或 OpenCode 自己保存的全部历史。

群聊还有额外限制。只有真实记忆所有者在本轮明确问起，才允许按规则召回私聊经历。含有私人记忆的群任务使用独立上下文，群共享历史只接收已经公开发出的回复。

## 文档知识库单独做

个人记忆适合保存偏好和经历，项目手册、接口说明与方法笔记则放进独立知识库。我为这部分接入了 LlamaIndex，向量索引仍使用 pgvector，同时用 Jieba 和 SQLite FTS5 做中文关键词检索。

文档需要明确导入。管理员可以从 WebUI 上传资料，普通聊天里收到一个 PDF 不会自动把它收进知识库。新版本索引完成后再切换，失败时保留旧版，避免一次更新把原来还能查到的资料一起弄丢。

检索会先限定当前可见的资料库，返回前再核对版本和权限。私人库只在管理员私聊使用，群聊只能访问明确开放给当前群的库。管理员在群里提问，也不会让私人库自动对这个群开放。

`knowledge_write` 允许管理员在私聊中提交方法笔记。受理后还要经过后台索引，工具接收成功不代表新版本已经可检索。笔记里也要区分参考步骤、已验证结果和失败记录。

记忆、文档与操作权限因此各自有了边界。检索到一份接口说明，可以据此理解参数；其中写着什么身份或命令，都不能改变当前任务的授权。

## QQ 原生能力也走同一套身份规则

继续补 QQ 功能时，我保留了 NapCat 的原生接口方案。模型先查接口目录和参数说明，再由桥接校验并执行。目录依据实际运行实例的 schema 生成，公开文档里存在一个接口，不代表当前安装版本已经注册它。

实际调用只开放给真实管理员任务。群里进一步限定为当前群的接口；读取私聊、跨群操作或修改账号资料，需要在管理员私聊提出。文档查询和实际操作分别判断权限。

这套工具同样记录调用回执。`confirmed` 表示 NapCat 已确认，`uncertain` 表示可能已经执行，不能换一个编号继续重发。敏感返回值只提供当前任务有效的不透明引用，完整凭据不进入模型正文和个人记忆。

工具能力越多，统一处理活动任务身份就越有用。附件与 NapCat 调用，以及记忆和知识库，都先找到真实任务，再检查各自的权限，减少每个模块自行解释身份的机会。

## 让补充消息接得上，也让状态查得到

私聊里经常会在任务开始后补一句要求。如果每句话都排成独立任务，模型可能等上一轮做完才看到更正。现在同一私聊在任务准备、执行或等待期间收到普通补充消息，会用 OpenCode `steer` 提交给当前任务。

补充消息单独保存来源和附件，随原任务恢复或取消，共用最终交付。桥接静默接收补充，不反复发固定确认。群聊继续排队，其他聊天不能插进来；进入交付阶段的新消息会安排到下一轮。

管理台则用于查看这套流程。它使用独立管理员账号，能看任务队列和历史会话，也能追查工具结果、记忆来源及知识索引状态。思考耗时只统计实际记录的时间戳，缺失就显示未记录。

历史会话映射可以显式切换，但需要确认聊天归属和任务空闲，不能把带私人记忆的上下文接回群共享会话。只读浏览使用独立连接，避免打开页面就触发数据库迁移或发送恢复。

## 最后整理出能带走的分发版

到 2026 年 10 月 27 日，我把通用副本发布成了 [QQ-OpenCode-Bridge](https://github.com/LianjinSe/QQ-OpenCode-Bridge)。整理过程中，除了排除密钥和数据库，还检查了写死的部署路径、固定文案，以及管理台的名称和头像。

分发版使用通用聊天人格。部署时需要给 OpenCode 一个独立工作目录，并把运行指引放进其中的 `AGENTS.md`。源码仓库里的维护指引面向开发 Agent，两份文件分别使用，不能互相覆盖。

![登录后的分发版管理台概览，使用隔离环境和示例任务数据](https://blog.lianjinse.cn/usr/uploads/2026/10/qq-opencode-bridge-dashboard.png)

两张图分别展示登录页和登录后的概览。概览在隔离环境中使用示例数据，展示任务列表和连接状态，不包含实际聊天、账号或服务器配置。

初始化脚本根据新机器的位置生成路径和 systemd 单元，并保留已有配置。四组原生工具分别合并安装，已有供应商和会话不用随之重置。部署文档也补齐了 NapCat、OpenCode 模型配置，以及 Mem0 和 LlamaIndex 的启用步骤。

分发整理时，556 项测试通过分批验证，另外检查了打包内容和 Compose 模板，并用匿名克隆验证初始化与四组插件合并。测试使用模拟 QQ 服务和本地假模型，不向真实 QQ 发送测试消息；这些检查也不能替代新部署对实际模型和账号的验证。

本机维护仓库与分发仓库现在分别保留历史。涉及功能变化时，完成改动和验证后，再决定是否同步公开版本；文档等非功能性修改按明确需要处理。公开仓库只保留通用内容，实际运行的配置和数据留在各自部署环境里。

## 接下来继续边用边改

这轮迭代保留了单进程的模块化结构。桥接负责装配组件，业务模块通过存储接口读写状态；原生工具共用身份解析，管理台各页面分别管理自己的异步请求。任务增加以后，可以沿着这些边界定位问题，暂时不需要再拆成一组独立服务。

项目还有继续完善的空间。每接入一种新能力，都要核对它如何确认成功、失败以后怎样恢复，以及结果应该回到哪个聊天。后续的使用问题和修改，也会继续记在项目文档里。

如果想自己部署，可以从仓库的 [README](https://github.com/LianjinSe/QQ-OpenCode-Bridge#readme) 和 [Agent 部署指引](https://github.com/LianjinSe/QQ-OpenCode-Bridge/blob/main/docs/DEPLOYMENT.md) 开始。通用人格和权限都可以按实际需求调整，不建议完全关闭权限控制。
